# Test data seeder — Phase 1 audit + build plan

Pre-build research for `scripts/seed-test-data.ts` + `scripts/verify-data-integrity.ts`.
Goal: ~2,200 records covering daily + monthly reservations, seasonal pricing,
payments, returns, expenses, maintenance blocks. Reproducible. Under 60 s.
Conducted 2026-05-25.

---

## TL;DR

| Area | Status |
| --- | --- |
| Prisma schema | Documented end-to-end (20+ models, 15+ enums). No surprises. |
| Existing seeders | **None.** No `prisma/seed.ts`, no `/scripts/*.ts`. Greenfield. |
| Invoice generation | `generateInvoicesForReservation()` in `lib/invoice-engine.ts` — script-callable. Reuse. |
| Pricing math | `getUnitPriceForRange()` in `lib/pricing.ts` — pure, importable. Reuse. |
| Supabase Auth | `createAdminClient()` already exists. `SUPABASE_SERVICE_ROLE_KEY` present in `.env`. |
| Sequence numbers | App-generated via `nextInvoiceNumber/PaymentNumber/ReturnNumber()`. Must be called in `$transaction`. |
| `@faker-js/faker` | **Not installed.** Recommend NOT adding — use hand-curated Omani name lists + deterministic indices for reproducibility. |
| Tooling | No `tsx` / `ts-node` in devDeps yet. Need to add one. |
| Multi-tenancy | `organizationId` on every meaningful row; safe deletion scope = two test-org IDs. |

**Headline:** infrastructure is in great shape. Library functions cover the
hardest math (pricing + invoice cycles + sequence numbers). The seeder
becomes mostly orchestration: insert orgs / users / units / tenants, then
call `generateInvoicesForReservation()` for each reservation, then record
payments and returns. ~1,200 lines of script + ~250 lines of verifier.

## 1. Schema cheat-sheet (the parts the seeder touches)

| Model | Required fields | Notes |
| --- | --- | --- |
| `Organization` | name | Defaults: city=Salalah, currency=OMR, timezone=Asia/Muscat |
| `User` | id (Supabase auth UUID), email, firstName, lastName, role | `organizationId` nullable during signup, set after onboarding. id must match Supabase auth.users.id. |
| `Property` | name, type, organizationId | type ∈ RESIDENTIAL / MIXED / HOTEL / COMMERCIAL |
| `Unit` | name, basePrice, propertyId | status defaults AVAILABLE |
| `UnitPrice` | unitId, priceType, dailyRate | priceType ∈ DEFAULT / SEASONAL. SEASONAL needs startDate/endDate + priority. |
| `Tenant` | firstName, lastName, phone, organizationId | tenantType ∈ individual/family/corporate/government. classification ∈ regular/vip/blacklisted. |
| `Reservation` | startDate, endDate, tenantId, status, totalNights, grandTotal | rateType ∈ "daily"/"monthly" (controls invoice cycles). `expectedInvoiceCount` for monthly. |
| `ReservationUnit` | reservationId, unitId, rateAmount, rateSource, nights, subtotal | Multi-unit reservations go here. `isMovedOut` + `movedToUnitId` for mid-stay swaps. |
| `ReservationActivity` | reservationId, organizationId, action | Audit trail. Will populate CREATED, CHECKED_IN, CHECKED_OUT, CANCELLED, NO_SHOW, EXTENDED, UNIT_MOVED, PAYMENT_RECORDED, RETURN_PROCESSED. |
| `Invoice` | invoiceNumber, organizationId, reservationId, tenantId, propertyId, totalAmount, status, dueDate | Status: PENDING / PARTIALLY_PAID / PAID / RETURNED / CANCELLED. |
| `InvoiceLineItem` | invoiceId, organizationId, description, quantity, unitPrice, lineTotal, rateType, rateSource | Generated by invoice engine; one per segment when stays cross seasonal boundaries. |
| `Payment` | amount, method, tenantId | Use PaymentAllocation to link to invoices. paymentNumber for new payments, null for legacy. |
| `PaymentAllocation` | paymentId, invoiceId, organizationId, amount | Unique on [paymentId, invoiceId]. |
| `Return` | returnNumber, organizationId, reservationId, tenantId, invoiceId, returnFrom, returnTo, returnDays, returnType, returnAmount | refundStatus ∈ NOT_REQUIRED / PENDING / COMPLETED. |
| `ReturnLineItem` | returnId, organizationId, description, quantity, unitPrice, lineTotal | One per refunded line. |
| `Expense` | expenseNumber, organizationId, categoryId, description, amount, propertyId, status, submittedById | status ∈ PENDING / APPROVED / REJECTED / PROCESSED. |
| `ExpenseCat` | organizationId, name, icon | System-defined categories per org. |

**Missing model:** the spec asks for 5 `MaintenanceBlock` records — there is no `MaintenanceBlock` model in the schema. The closest is `Unit.status = MAINTENANCE`. **Decision needed (see §6).**

## 2. The build, in 6 phases

### Phase A — Setup (1 commit)

- Add `tsx` to devDeps (preferred over `ts-node` — zero config, native ESM).
- Add npm scripts: `"seed:test": "tsx scripts/seed-test-data.ts"`, `"verify:integrity": "tsx scripts/verify-data-integrity.ts"`.
- Create `scripts/seed-test-data.ts` skeleton with phase headers + summary.
- Create `scripts/_seed/` helpers folder:
  - `omani-names.ts` — curated lists (40 male first names, 40 female, 40 surnames, Arabic variants, nationalities).
  - `rand.ts` — deterministic PRNG seeded with a constant so re-runs produce identical data.
  - `dates.ts` — thin wrapper around date-fns for the specific date arithmetic the seeder needs.

### Phase B — Org + users + properties + units + seasonal pricing (1 commit)

- Create `Al Noor Property Management` + `Salalah Suites` orgs.
- For each test user: `admin.auth.admin.createUser({ email, password })` → take returned `user.id` → insert matching Prisma `User` with that id + organizationId.
- 4 properties: 3 for Al Noor + 1 for Salalah Suites.
- 33 units (Al Noor) by the spec breakdown + ~6 for Salalah Suites.
- For every unit, 1 DEFAULT UnitPrice + 3 SEASONAL UnitPrices (Khareef 2025, Khareef 2026, Eid 2026).
- Seed system expense categories (Maintenance, Cleaning, Supplies, Utilities, etc.) per org.

### Phase C — Tenants (1 commit)

- 60 tenants by spec distribution (40 individual Omani / 8 family / 7 corporate / 3 government, 2 VIP, 1 blacklisted, 10 with Arabic names).
- Nationality distribution: 60% Omani / 20% Saudi+UAE / 10% Yemeni / 10% other.
- Phone: deterministic Omani format `+968 9XXX XXXX`.
- ~5 extra tenants on Salalah Suites for multi-tenancy testing.

### Phase D — Reservations (1 commit, the big one)

- 70 daily reservations with the 8 sub-statuses spec'd.
- 50 monthly reservations with the 5 sub-statuses spec'd.
- ReservationUnit rows per reservation (most single-unit, 1 with 4 units for the edge case).
- ReservationActivity for each non-trivial state transition.
- The 10 edge cases woven in:
  1. Khareef boundary crossings — 2 reservations spanning Jun 28–Jul 5 / Aug 28–Sep 4.
  2. Full Khareef span — 1 reservation Jun 28–Sep 4.
  3. Multi-unit — 1 reservation with 4 units.
  4. Mixed invoice statuses — 1 reservation with PAID + PARTIALLY_PAID + PENDING invoices.
  5. Repeat guest — 1 tenant with 5+ historical reservations.
  6. Low occupancy building — Salalah Plaza target 40%.
  7. High occupancy building — Al Noor Residence target 90%+.
  8. Extended reservation — 1 reservation with EXTENDED activity log + adjusted endDate.
  9. Unit changed mid-stay — 1 ReservationUnit with `isMovedOut=true`, `movedToUnitId`, `moveDate` + UNIT_MOVED activity.
  10. Multiple simultaneous overstays — already covered by spec's "2 overstaying" + add 2 more.

Each reservation gets its invoices via `generateInvoicesForReservation()`. This is the heaviest phase by line count and CPU time. Will batch in Promise.all where safe.

### Phase E — Payments + returns + expenses + maintenance (1 commit)

- Payments per spec distribution (60% cash / 25% bank / 10% card / 5% cheque).
- 12 partial payment scenarios — payment amount < invoice total.
- 12 returns: 8 daily + 4 monthly. For monthly returns, also cancel the future invoices on the same reservation.
- 50 expenses by the status breakdown, distributed across 3 buildings + 7 categories.
- Maintenance — see §6 decision.

### Phase F — Verification script (1 commit)

- `scripts/verify-data-integrity.ts` runs all 9 checks the spec lists.
- Each check returns PASS/FAIL + a one-line reason.
- Console output is a table with status, check name, detail.
- Exit code: 0 if all pass, 1 if any fail.

### Phase G — README + docs (1 commit)

- `scripts/README.md` documents how to run, what gets seeded, how to log in, what edge cases are covered.

## 4. Performance — making the 60 s budget

- Use `$transaction([...])` for bulk-related inserts (Prisma supports arrays of operations).
- Use `createMany()` for the obvious bulk inserts (UnitPrices, Tenants, ReservationActivities).
- Run the 120 invoice generations in batches of 8 with `Promise.all` (Postgres connection pool default = 10).
- Supabase auth user creation is sequential (the admin SDK's `createUser` is per-request); 6 users × ~200 ms = 1.2 s. Fine.
- Expected runtime: 15–45 s on a healthy connection. Tight but achievable.

---

## 5. Auth user re-runs

`admin.auth.admin.createUser()` errors with `"User already registered"` on the 2nd run. Three options:

1. **Idempotent seeder — delete first.** Before re-creating, list users by email, call `admin.auth.admin.deleteUser(id)` for each. Simplest semantics: every run starts clean.
2. **Reuse — check exists first.** `admin.auth.admin.listUsers({ filter: ... })`, take existing id if found. More complex; risks stale passwords if you change the seed.
3. **One-shot — error out.** Throw if any user exists; user runs a manual cleanup first.

**Recommendation:** option (1). Re-running `npm run seed:test` always produces the same dataset.

## 6. The `MaintenanceBlock` decision

The spec asks for 5 maintenance blocks: 2 current, 3 past. The schema has no `MaintenanceBlock` model. Three ways to interpret:

1. **Use Unit.status = MAINTENANCE.** Cleanest for "current" blocks. But the schema can't represent the duration of a past block.
2. **Encode as ReservationActivity entries.** Doesn't fit cleanly — activities are reservation-scoped.
3. **Skip the past blocks.** Set 2 units to MAINTENANCE for "currently blocked", mention the limitation in the README.

**Recommendation:** option (3). 2 units → MAINTENANCE status. Note the lack of historical maintenance tracking in the README. If the user wants past blocks tracked, that's a schema migration outside this scope.

## 9. Risks I cannot verify from the CLI

I cannot run the seeder against your database to confirm it works. The script will be carefully typechecked, but there are runtime failure modes I'd want to flag:

- **Connection pool exhaustion** if the parallel invoice generations exceed Prisma's default 10. I'll cap concurrency at 5 to be safe.
- **Supabase admin rate limits** if you re-run the seeder very frequently — Supabase will throttle auth calls. Spec'd backoff: 100 ms between user deletions/creations.
- **The `generateInvoicesForReservation()` function** may throw if the reservation already has invoices (`invoicesGenerated=true`). The seeder constructs fresh reservations so this should never fire, but if you re-run mid-failure the partial state could cause issues. The cleanup step in option (1) handles this.
- **Service role key in env** — the audit confirms it's in `.env`. Verify it's loaded before the seeder runs.

I'd recommend doing a dry-run on a development branch of the database first.
