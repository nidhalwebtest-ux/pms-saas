# Test data seeder

Generates ~2,200 records of realistic Omani PMS test data for local
development, QA, and demo runs.

---

## Quick start

```bash
npm run seed:test         # populate the database
npm run verify:integrity  # run nine integrity checks
```

Re-run anytime — the seeder is idempotent. It deletes the two test orgs
(and their Supabase auth users) before re-creating everything from scratch.

**Production data on other orgs is never touched.**

## Edge cases covered

Per the spec, every reservation/invoice scenario QA needs is represented:

1. **Khareef boundary crossings** — reservations spanning Jun 28 → Jul 5 and Aug 28 → Sep 4 (forces seasonal segmentation).
2. **Full Khareef span** — one monthly reservation Jun 28 → Sep 4 2026.
3. **Multi-unit reservation** — one tenant with 4 units in a single booking.
4. **Mixed invoice statuses** — partial payment + overdue scenarios populated across active monthly stays.
5. **Repeat guest** — first individual tenant has 5+ historical reservations.
6. **Low occupancy building** — Salalah Plaza targets ~40% (8 units, few active).
7. **High occupancy building** — Al Noor Residence targets ~90%+.
8. **Extended reservation** — one reservation with an EXTENDED activity log + adjusted endDate.
9. **Mid-stay unit swap** — one ReservationUnit with `isMovedOut=true`, `movedToUnitId`, `moveDate` + UNIT_MOVED activity.
10. **Multiple simultaneous overstays** — 2 reservations spec'd as overstaying today.

## Integrity checks

`npm run verify:integrity` runs nine checks and exits non-zero if any fail:

1. Invoice amounts match reservation rates × duration (seasonal-aware tolerance)
2. Payment allocations don't exceed invoice totals
3. Invoice status matches payment state (PENDING / PARTIALLY_PAID / PAID)
4. Tenant balances calculated correctly (no overpayments)
5. No double-booked units
6. Unit status matches reservation status (CHECKED_IN → OCCUPIED)
7. Monthly invoice count matches `expectedInvoiceCount` (±2 tolerance for early-checkout cycles)
8. Cancelled invoices excluded from payment allocations
9. Seasonal pricing correctly applied to dates in Khareef / Eid

## Known limitations

- **MaintenanceBlock model not in schema.** The spec called for 5
  maintenance blocks (2 current + 3 past). The closest we have is
  `Unit.status = MAINTENANCE`, which represents "currently blocked" but
  cannot record historical maintenance with duration. We set 2 units to
  MAINTENANCE for the current scenarios; the 3 past blocks are skipped.
  To track past blocks, add a `MaintenanceBlock` model in a Prisma
  migration outside this seeder's scope.

- **Reservation numbers** are not back-filled. The schema's
  `reservationNumber` field is nullable and currently unused in the app;
  the seeder leaves it null.

- **Tax / VAT** is `0` on all invoices, matching the production engine's
  current behaviour (`CLAUDE.md` notes tax is configurable later via org
  settings).

- **Salalah Suites** gets 1 admin user + 1 building + 6 units + 5 tenants
  + zero reservations. Just enough to verify multi-tenant isolation works.

## Architecture

```
scripts/
  seed-test-data.ts          # orchestrator + cleanup + summary
  verify-data-integrity.ts   # nine integrity checks
  _seed/
    rand.ts                  # deterministic PRNG (Mulberry32 + fixed seed)
    omani-names.ts           # curated name + nationality + corporate lists
    dates.ts                 # date helpers + Khareef / Eid window constants
    setup.ts                 # Phase B — orgs, users, properties, units, prices
    tenants.ts               # Phase C — 65 tenants
    reservations.ts          # Phase D — 120 reservations + invoices
    financials.ts            # Phase E — payments, returns, expenses, maintenance
```

The seeder calls `generateInvoicesForReservation()` from
`lib/invoice-engine.ts` for every non-cancelled reservation so invoice
math (seasonal segmentation, monthly cycles, pro-ration) is identical to
production behaviour — no math is duplicated in the seeder.

## Re-running after schema changes

If a Prisma migration changes a required field on any seeded model:

1. Run the migration: `npx prisma migrate dev`
2. Update the corresponding `_seed/*.ts` file to populate the new field.
3. Re-run the seeder: `npm run seed:test`.

The seeder fails fast with a Prisma validation error; the error message
will point at the missing field.
