# Performance audit — 19 Nov 2026 (Roadmap item 1, round 1)

## Root cause: the functions run far from the database

| | Location |
|---|---|
| Vercel functions (`x-vercel-id`) | **bom1, Mumbai** |
| Supabase Postgres + Auth | **eu-west-1, Ireland** |

### What one query costs

Measured from a client about as far from Ireland as Mumbai is:

| Connection | One query | Round trips per query |
|---|---|---|
| Transaction pooler `:6543` with `pgbouncer=true` (what production uses) | **~775 ms** | ~5 |
| Session mode `:5432` | ~156 ms | 1 |

Prisma makes about 5 round trips per query through the transaction pooler. At a Mumbai–Ireland distance, that is roughly **600 ms per query in production**. Requests run one after another, so the cost adds up:

- **Public site home page:** about 3 sequential queries, measured at ~1.6–1.8 s TTFB.
- **A dashboard page, estimated from the code:**
  - middleware Auth check: ~250 ms
  - layout: Auth plus 4 sequential queries
  - page: repeats the Auth call and the user lookup, then runs its own queries
  - total: **about 4–5 s**, almost all of it network wait.

| URL | TTFB | HTML KB | region | cache |
|---|---|---|---|---|
| www.binaya.app/ | 148 ms | 371 | bom1→bom1 | MISS |

Dashboard pages need a login, so measure them with `PERF_COOKIE` (see the header of the script) before and after the deploy.

## Changes in this round

1. **`vercel.json` → `"regions": ["dub1"]`.** Functions move to Dublin, the same AWS region as the database.
   - A query round trip drops from ~120 ms to ~1 ms, so the 5-round-trip pooler cost becomes ~5 ms.
   - The user's browser now makes **one** longer trip (Oman ↔ Dublin, ~100–130 ms) instead of the server making dozens of Mumbai ↔ Ireland trips.
2. **Dashboard layout:** the super-admin check, building scope, property list, selected building and website-request badge count now run in one `Promise.all`. Before, they ran in 3–4 sequential steps.
   - Building scope is now applied through the relation, so the property list no longer waits for the assignment lookup.
   - Checked against all 10 real users (same results as before) and against a restricted user inside a rolled-back transaction.
3. **34 dashboard pages and `lib/route-guard.ts`** used `supabase.auth.getUser()` directly, so each page repeated the Auth network call the layout had already made. They now use the request-cached `getAuthUser()` / `getSessionUser()`.
4. **Translations:** the root layout used to send the full dictionary (31 sections, 260 KB in English / 333 KB in Arabic) on every page load. Now:
   - Public pages get `common, marketing, auth, phoneInput` only.
   - Tenant booking sites get nothing (they use their own dictionary).
   - Dashboard, admin, onboarding and invite re-provide the full set through a nested provider (`components/FullMessagesProvider.tsx`).
   - Local production-build results:

     | Page | HTML before | HTML after |
     |---|---|---|
     | Landing | 371 KB | 173 KB |
     | Login | 240 KB | 39 KB |
     | Tenant site | 305 KB | 87 KB |

   - Landing, login and contact were checked in a headless browser in EN and AR: no console errors and no raw translation keys.
5. **Privacy fix:** Binaya's Google Analytics no longer loads on customers' booking sites. Only the Meta pixel was excluded before.
