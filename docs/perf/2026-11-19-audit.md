# Performance audit — 19 Nov 2026 (Roadmap item 1, round 1)

## Root cause: the functions run far from the database

| | Location |
|---|---|
| Vercel functions (`x-vercel-id`) | **bom1, Mumbai** |
| Supabase Postgres + Auth | **eu-west-1, Ireland** |

### What one query costs

Measured from a client about as far from Ireland as Mumbai is:

| Connection | One query | Round trips per query |
|---|---|---|
| Transaction pooler `:6543` with `pgbouncer=true` (what production uses) | **~775 ms** | ~5 |
| Session mode `:5432` | ~156 ms | 1 |

Prisma makes about 5 round trips per query through the transaction pooler. At a Mumbai–Ireland distance, that is roughly **600 ms per query in production**. Requests run one after another, so the cost adds up:

- **Public site home page:** about 3 sequential queries, measured at ~1.6–1.8 s TTFB.
- **A dashboard page, estimated from the code:**
  - middleware Auth check: ~250 ms
  - layout: Auth plus 4 sequential queries
  - page: repeats the Auth call and the user lookup, then runs its own queries
  - total: **about 4–5 s**, almost all of it network wait.

`node scripts/perf/measure.mjs`, 5 runs, median:

|---|---|---|---|---|
| www.binaya.app/ | 148 ms | 371 | bom1→bom1 | MISS |
| www.binaya.app/login | 123 ms | 240 | bom1→bom1 | MISS |
| demo.binaya.app/ | **1611 ms** | 305 | bom1→bom1 | MISS |
| demo.binaya.app/buildings | **1590 ms** | 275 | bom1→bom1 | MISS |

Dashboard pages need a login, so measure them with `PERF_COOKIE` (see the header of the script) before and after the deploy.

## Changes in this round

1. **`vercel.json` → `"regions": ["dub1"]`.** Functions move to Dublin, the same AWS region as the database.
   - A query round trip drops from ~120 ms to ~1 ms, so the 5-round-trip pooler cost becomes ~5 ms.
   - The user's browser now makes **one** longer trip (Oman ↔ Dublin, ~100–130 ms) instead of the server making dozens of Mumbai ↔ Ireland trips.
2. **Dashboard layout:** the super-admin check, building scope, property list, selected building and website-request badge count now run in one `Promise.all`. Before, they ran in 3–4 sequential steps.
   - Building scope is now applied through the relation, so the property list no longer waits for the assignment lookup.
   - Checked against all 10 real users (same results as before) and against a restricted user inside a rolled-back transaction.
3. **34 dashboard pages and `lib/route-guard.ts`** used `supabase.auth.getUser()` directly, so each page repeated the Auth network call the layout had already made. They now use the request-cached `getAuthUser()` / `getSessionUser()`.
4. **Translations:** the root layout used to send the full dictionary (31 sections, 260 KB in English / 333 KB in Arabic) on every page load. Now:
   - Public pages get `common, marketing, auth, phoneInput` only.
   - Tenant booking sites get nothing (they use their own dictionary).
   - Dashboard, admin, onboarding and invite re-provide the full set through a nested provider (`components/FullMessagesProvider.tsx`).
   - Local production-build results:

     | Page | HTML before | HTML after |
     |---|---|---|
     | Landing | 371 KB | 173 KB |
     | Login | 240 KB | 39 KB |
     | Tenant site | 305 KB | 87 KB |

   - Landing, login and contact were checked in a headless browser in EN and AR: no console errors and no raw translation keys.
5. **Privacy fix:** Binaya's Google Analytics no longer loads on customers' booking sites. Only the Meta pixel was excluded before.

## After (production, commit 76f145a promoted)

`node scripts/perf/measure.mjs`, 5 runs, median. The function region is now **dub1**:

| URL | TTFB before → after | HTML KB before → after |
|---|---|---|
| www.binaya.app/ | 148 → 275 ms | 371 → 169 |
| www.binaya.app/login | 123 → 244 ms | 240 → 38 |
| demo.binaya.app/ | **1611 → 311 ms (5.2× faster)** | 305 → 85 |
| demo.binaya.app/buildings | **1590 → 274 ms (5.8× faster)** | 275 → 55 |

Pages with no database work got about 120 ms slower to first byte. That is the longer network trip to Dublin, and it is outweighed by the HTML being 55–85% smaller. Every page that queries the database got 5–6× faster.

# Round 2 — 19 Nov 2026

## What the database itself says

`pg_stat_statements` (counting since July 2026) shows the slowest queries **average 0.3–12 ms of actual execution**. SQL speed was never the problem. The cost was network round trips, which round 1 fixed.

## Code review of the main pages and actions

| Path | What we found | Status |
|---|---|---|
| `/api/dashboard/today` and `/api/dashboard/manager` (dashboard home data) | All queries already run in one parallel batch | OK |
| Invoices and payments list pages | About 5 short sequential steps, mostly cached per request | OK now that the functions are in dub1 (~a few ms each) |
| Generate invoices (monthly) | Each billing cycle is its own transaction of ~4–6 sequential steps, because invoice-number locking requires that order. A 12-month lease is ~70 steps. | Was about 40 s in bom1. Now well under 1 s in dub1. No code change needed. |
| Record payment, create reservation, check-in | ~10–15 sequential steps inside one transaction | ~50–100 ms in dub1 |

## Changes

1. **Public-site data cached across requests** (`lib/public-site/data.ts`): site settings, buildings and units, for 60 s.
   - Availability search and quotes are **not** cached; they stay live.
   - Saving, publishing or changing the status of a website clears the cache immediately (`updateTag` in `app/dashboard/settings/website/actions.ts`). That includes the old address when a site's slug is renamed.
   - Building and unit edits made elsewhere in the PMS appear within 60 s.
   - Locally, a repeat visit to a tenant page took **~30 ms instead of several seconds**.
2. **Middleware uses `getClaims()` instead of `getUser()`.**
   - The project signs tokens with ES256 keys (checked against the public JWKS), so the token is verified locally and every request skips a network call to Supabase Auth.
   - If verification ever fails, it falls back to `getUser()`, so a valid user is never redirected to `/login` by mistake.
   - Pages and routes still call `getUser()`, which is the authoritative check and still rejects a revoked user immediately.
   - Tested: no cookie and a garbage cookie both redirect to `/login`. Not yet tested with a real logged-in session; check that on Preview.
3. **Client JavaScript.** Measured as the total JS a page loads (`<script>` tags):

   | Page | Before | After |
   |---|---|---|
   | `/login` | 1,407 KB (405 gz) | **737 KB (227 gz)**, −48% |
   | `/verify-email` | 1,393 KB | **720 KB** |
   | `/` (landing) | 1,134 KB (350 gz) | **923 KB (295 gz)** |

   - Cause: importing one component from the `@/components/ui` barrel file pulls in the **whole** UI kit (~426 KB chunk). Login, verify-email, onboarding and invite now import directly from the component file.
   - The landing page's Demo Tour modal (Headless UI and form fields) now loads only when needed: on hover or focus of the button, and when it's clicked. Checked in Chrome in EN and AR: the modal opens with its form and there are no errors.
